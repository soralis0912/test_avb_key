## 4. 脆弱性情報

### 4-1. 脆弱性の種類

- 既知の（公開された）暗号鍵の使用 — CWE-321: Use of Hard-coded Cryptographic Key
- 関連：CWE-798（ハードコードされた認証情報の使用）、CWE-347（暗号署名の不適切な検証）
- 分類（IPA 選択肢）：**その他（暗号技術の不適切な使用 / セキュアブートの迂回）**

### 4-2. 脆弱性の内容

Android 端末では、ブートローダが `vbmeta` パーティションの署名を検証し、その内容（各パーティションの
ハッシュ／ハッシュツリー記述子）に基づいて `boot` / `system` / `vendor` などのパーティションの完全性を
検証する Android Verified Boot（AVB）が実装されています。この仕組みの安全性は、**vbmeta の署名鍵の
秘密鍵が製品開発者のみに秘匿されていること**を前提としています。

しかし対象製品の出荷ファームウェア（user ビルド）の `vbmeta` は、**AOSP のソースツリー内に
秘密鍵そのものが公開されているテスト用鍵**（`external/avb/test/data/testkey_rsa4096.pem` 等。
本来は userdebug／開発ビルド専用）で署名されていました。

この秘密鍵は誰でも取得可能であるため、攻撃者は **任意に改変した boot / system / vendor イメージと、
それに対応する vbmeta を自ら正当に署名して作成できます**。生成した vbmeta はブートローダの検証を
正規に通過するため、ブートローダがロックされたままの状態（Verified Boot state = GREEN、警告画面なし）
でも、改ざんされた OS が正規のものとして起動します。

すなわち、ブートローダのロックや e-Fuse による Root of Trust の設定が正しく行われていても、
**Verified Boot による改ざん検知が事実上無効化されている**状態です。

なお、AVB の公開鍵（またはそのハッシュ）はブートローダ側／e-Fuse 側に焼き込まれているため、
本問題の是正には通常、ブートローダを含めた署名鍵の入れ替えが必要となり、
**通常の OTA によるアプリ層の修正では解消できない**点にご留意ください。

参考：本問題の一般的な解説および検査ツール（NCC Group）
- https://www.nccgroup.com/research-blog/on-almost-signing-android-builds/
- https://github.com/nccgroup/test_avb_key
- Android Verified Boot: https://source.android.com/docs/security/features/verifiedboot

### 4-3. 再現手順（検証方法）

1. 対象端末の `vbmeta` イメージを取得する。
   - 公式配布ファームウェア（工場出荷イメージ／OTA パッケージ）から `vbmeta.img` を抽出する、または
   - 端末上から該当ブロックデバイスを吸い出す。
     ```
     dd if=/dev/block/by-name/vbmeta of=/sdcard/vbmeta.img
     ```
2. AOSP の公開テスト鍵を取得する。
   ```
   git clone https://android.googlesource.com/platform/external/avb
   # 秘密鍵は avb/test/data/testkey_rsa2048.pem, testkey_rsa4096.pem, testkey_rsa8192.pem 等
   ```
3. 公開検査ツールで、vbmeta 内に公開テスト鍵の公開鍵（モジュラス）が含まれるかを検査する。
   ```
   git clone https://github.com/nccgroup/test_avb_key
   python3 test_avb_key.py ./vbmeta.img ./avb/test/data/
   ```
4. 出力の確認。テスト鍵で署名されている場合、以下のように該当鍵で `Public key found` が出力される。

   ```
   Opening vbmeta file: ./vbmeta.img

   Using known private key for verification: ./avb/test/data/testkey_rsa2048.pem. Public key not found in vbmeta.img file. That's good.
   ...
   Using known private key for verification: ./avb/test/data/testkey_rsa4096.pem. Public key found at index: 【要記入：実際の値】
   If the script was executed on a vbmeta.img file from an Android user build, there is a problem.
   ```

   【要記入：Rakuten Hand 5G / D-52A それぞれについて、一致したテスト鍵ファイル名と実際の出力を貼付】

5. 併せて、以下でも同一の公開鍵が使用されていることを確認できる（補助的確認）。
   ```
   avbtool info_image --image vbmeta.img
   python3 avbtool extract_public_key --key testkey_rsa4096.pem --output pubkey.bin
   # vbmeta.img 内に pubkey.bin と一致するバイト列が存在すること
   ```

> 注意：検証は当方が保有する端末に対してのみ実施しており、第三者の端末や
> 提供事業者のシステムに対する試験・改変は一切行っていません。
> また、実際に改ざんイメージを署名して端末に書き込む攻撃の実証（PoC）は【要記入：実施していない／
> 自身の所有端末に限り実施した】。

### 4-4. 脆弱性により発生しうる脅威

本脆弱性により、攻撃者は AVB の検証を通過する改ざんファームウェアを作成・適用できます。想定される脅威は以下のとおりです。

1. **セキュアブート（Verified Boot）の迂回**：改ざんされた OS が、警告表示なく正規イメージとして起動する。
   利用者は端末が改ざんされていることを認識できない。
2. **端末上での恒久的な任意コード実行**：root 権限で動作するコードの埋め込み、SELinux ポリシーの無効化、
   `boot` / `system` / `vendor` パーティションへのバックドア設置が可能。工場出荷状態へのリセットでも除去されない。
3. **利用者情報の窃取**：認証情報、通信内容、メッセージ、位置情報、決済アプリの取扱い情報等の窃取。
   画面ロック解除情報の詐取（改ざんした OS によるロック画面の偽装等）も理論上可能。
4. **端末セキュリティ機構の無効化**：Verified Boot に依存する各種保護（改ざん検知、
   Key Attestation を利用したアプリ側の完全性検証等）の信頼性が損なわれる。
5. **サプライチェーン／中古端末流通経路での悪用（いわゆる evil maid 攻撃）**：
   端末を一時的に物理的に扱える立場の者（修理・中古買取・輸送・貸与端末の返却時等）が、
   検知困難な改ざんを施した端末を利用者に渡すことが可能。

**攻撃条件**：端末への物理的アクセス、または何らかの手段でパーティションへの書き込み権限を
得られること。事前の特別な権限や利用者操作は必要としない。

**CVSS v3.1（参考値・届出者評価）**
- 基本値：**7.6（High）**
- ベクタ：`CVSS:3.1/AV:P/AC:L/PR:N/UI:N/S:C/C:H/I:H/A:H`
- 選定理由：物理アクセスまたはパーティション書き込み経路を要する（AV:P）が、
  ブートローダのロックという端末の信頼境界そのものを越えるため Scope は Changed（S:C）とした。

### 4-5. 回避策・対策

**利用者側の回避策**
- 有効な回避策はありません（署名鍵はファームウェアに固定されており、利用者設定では変更できません）。
- 緩和策として、端末を第三者に物理的に預けない、信頼できない中古端末・貸与端末を業務利用しない、
  といった運用上の注意にとどまります。

**製品開発者側の推奨対策**
1. 出荷（user）ビルドの署名を、**製品開発者が秘匿管理する製品固有の AVB 鍵**に切り替える。
2. 併せて、ブートローダ／e-Fuse 側に焼き込まれた Root of Trust（AVB 公開鍵ハッシュ）を
   更新する必要があるため、出荷済み端末への配信可否・手順を検討する。
3. リリースビルドで `external/avb/test/data/` 配下の鍵が使用されないよう、
   ビルド設定（`BOARD_AVB_KEY_PATH` 等）を確認し、**テスト鍵が使われた場合にビルドを失敗させる
   チェックを CI／リリース工程に組み込む**（前掲の検査ツールはこの用途にも利用可能）。
4. 同一のビルド基盤を共用する他機種についても横展開して確認する。
5. AVB のロールバックインデックス運用（`rollback_index`）の適切な設定を併せて確認する。
