## 4. 脆弱性情報

### 4-1. 脆弱性の種類

- 既知の（公開された）暗号鍵の使用 — CWE-321: Use of Hard-coded Cryptographic Key
- 関連：CWE-798（ハードコードされた認証情報の使用）、CWE-347（暗号署名の不適切な検証）
- 分類（IPA 選択肢）：**その他（暗号技術の不適切な使用 / セキュアブートの迂回）**

### 4-2. 脆弱性の内容

Android 端末では、ブートローダが `vbmeta` パーティションの署名を検証し、その内容（各パーティションの
ハッシュ／ハッシュツリー記述子）に基づいて `boot` / `init_boot` / `system` / `vendor` などのパーティションの
完全性を検証する Android Verified Boot（AVB）が実装されています。この仕組みの安全性は、
**vbmeta の署名鍵の秘密鍵が製品開発者のみに秘匿されていること**を前提としています。

しかし対象製品の出荷ファームウェア（user ビルド）の `vbmeta` は、**AOSP のソースツリー内に
秘密鍵そのものが公開されているテスト用鍵**（`external/avb/test/data/testkey_rsa*.pem`。
本来は userdebug／開発ビルド専用）で署名されていました。

この秘密鍵は誰でも取得可能であるため、攻撃者は **任意に改変した boot / init_boot / system / vendor イメージと、
それに対応する vbmeta を自ら正当に署名して作成できます**。生成した vbmeta はブートローダの検証を
正規に通過するため、ブートローダがロックされたままの状態（Verified Boot state = GREEN、警告画面なし）
でも、改ざんされた OS が正規のものとして起動します。

すなわち、ブートローダのロックや e-Fuse による Root of Trust の設定が正しく行われていても、
**Verified Boot による改ざん検知が事実上無効化されている**状態です。

**本脆弱性が特に重大である理由**は、AVB が本来担っている「一時的な権限昇格を、恒久的な端末乗っ取りに
昇格させない」という防御線が機能しない点にあります。通常、カーネル等の脆弱性で一時的に root 権限を
取得できたとしても、ブートイメージを書き換えれば次回起動時に Verified Boot が検知して起動を拒否するため、
再起動により改ざんは無効化されます。しかし本脆弱性が存在する端末では、攻撃者が公開テスト鍵で
正当な署名を付与できるため、**再起動後も検知されずに改ざんが維持され、初期化（factory reset）でも
除去されない恒久的な侵害が成立します**。当方はこの経路を実機で確認しています（4-3 参照）。

なお、AVB の公開鍵（またはそのハッシュ）はブートローダ側／e-Fuse 側に焼き込まれているため、
本問題の是正には通常、ブートローダを含めた署名鍵の入れ替えが必要となり、
**通常の OTA によるアプリ層の修正では解消できない**点にご留意ください。

参考：本問題の一般的な解説および検査ツール（NCC Group）
- https://www.nccgroup.com/research-blog/on-almost-signing-android-builds/
- https://github.com/nccgroup/test_avb_key
- Android Verified Boot: https://source.android.com/docs/security/features/verifiedboot

### 4-3. 再現手順（検証方法）

#### (1) テスト鍵で署名されていることの確認

1. 対象端末の `vbmeta` イメージを取得する。
   - 公式配布ファームウェア（工場出荷イメージ／OTA パッケージ）から `vbmeta.img` を抽出する、または
   - 端末上から該当ブロックデバイスを吸い出す。
     ```
     dd if=/dev/block/by-name/vbmeta of=/sdcard/vbmeta.img
     ```
2. AOSP の公開テスト鍵を取得する。
   ```
   git clone https://android.googlesource.com/platform/external/avb
   # 秘密鍵は avb/test/data/testkey_rsa2048.pem, testkey_rsa4096.pem, testkey_rsa8192.pem 等
   ```
3. 公開検査ツールで、vbmeta 内に公開テスト鍵の公開鍵（モジュラス）が含まれるかを検査する。
   ```
   git clone https://github.com/nccgroup/test_avb_key
   python3 test_avb_key.py ./vbmeta.img ./avb/test/data/
   ```
4. 出力の確認。テスト鍵で署名されている場合、以下のように該当鍵で `Public key found` が出力される。

   ```
   Opening vbmeta file: ./vbmeta.img

   Using known private key for verification: ./avb/test/data/testkey_rsa2048.pem. Public key not found in vbmeta.img file. That's good.
   ...
   Using known private key for verification: ./avb/test/data/testkey_rsa4096.pem. Public key found at index: 【要記入：実際の値】
   If the script was executed on a vbmeta.img file from an Android user build, there is a problem.
   ```

   【要記入：Rakuten Hand 5G / dtab Compact d-52C それぞれについて、一致したテスト鍵ファイル名と実際の出力を貼付】

5. 補助的確認として、以下でも同一の公開鍵が使用されていることを確認できる。
   ```
   avbtool info_image --image vbmeta.img
   python3 avbtool extract_public_key --key testkey_rsa4096.pem --output pubkey.bin
   # vbmeta.img 内に pubkey.bin と一致するバイト列が存在すること
   ```

#### (2) 実機における影響の実証（Rakuten Hand 5G、当方所有端末にて実施）

以下は、**ブートローダのアンロックを行わずに**（＝出荷状態のロックされたブートローダのまま）
改ざんイメージを起動させられることの確認手順です。

1. 端末上のローカル権限昇格の脆弱性（Qualcomm Adreno GPU の **KGSL ドライバの脆弱性**、
   【要記入：CVE 番号がわかれば記載。例 CVE-20XX-XXXXX】）を利用し、root 権限を取得した。
2. 取得した root 権限で、`init_boot`（および `vbmeta`）パーティションの内容を改変した。
3. 改変後のイメージに対し、**公開されている AOSP テスト鍵（秘密鍵）を用いて `avbtool` で署名**し、
   対応する `vbmeta` を再生成した。
   ```
   avbtool add_hash_footer --image init_boot_modified.img --partition_name init_boot \
       --partition_size <SIZE> --key testkey_rsa4096.pem --algorithm SHA256_RSA4096
   avbtool make_vbmeta_image --key testkey_rsa4096.pem --algorithm SHA256_RSA4096 \
       --include_descriptors_from_image init_boot_modified.img ... --output vbmeta_modified.img
   ```
4. 生成したイメージを各パーティションへ書き込んだ。
   ```
   dd if=init_boot_modified.img of=/dev/block/by-name/init_boot
   dd if=vbmeta_modified.img   of=/dev/block/by-name/vbmeta
   ```
5. 端末を再起動したところ、**警告画面や起動拒否は発生せず、改ざんしたイメージがそのまま起動した**。
   ブートローダはロックされたままであり、Verified Boot の検証は「正常」として通過した。

   → 署名鍵が製品固有の秘匿鍵であれば、手順 3 の署名が作成できないため手順 5 で起動が拒否され、
     一時的な root 権限の取得は再起動により無効化されるはずである。本脆弱性により、それが成立していない。

> **補足（別脆弱性の可能性）**：手順 1 で利用した KGSL ドライバの脆弱性は、
> 検証時点の最新ファームウェアで動作しました。当該脆弱性が未修正である場合、
> 本届出とは**別個の脆弱性**として取り扱われるべきものと考えます。
> 必要であれば別途届出いたしますので、ご指示ください。
> 【要記入：既知の CVE か、修正済みか、別途届出済みか】

> **検証範囲について**：検証は当方が正当に保有する端末に対してのみ実施しており、
> 第三者の端末、通信事業者の設備、製品開発者のシステムに対する試験・改変は一切行っていません。
> 攻撃コードの公開も行っていません。

### 4-4. 脆弱性により発生しうる脅威

本脆弱性により、攻撃者は AVB の検証を通過する改ざんファームウェアを作成・適用できます。想定される脅威は以下のとおりです。

1. **セキュアブート（Verified Boot）の迂回**：改ざんされた OS が、警告表示なく正規イメージとして起動する。
   利用者は端末が改ざんされていることを認識できない（実機で確認済み）。
2. **一時的な権限昇格の恒久化**：ローカル権限昇格の脆弱性（今回は KGSL ドライバの脆弱性を使用）と
   組み合わせることで、**再起動やファクトリーリセットでも除去されない恒久的なバックドア**を設置できる。
   本来 AVB が担うべき「侵害の封じ込め」が機能しない。
3. **端末上での恒久的な任意コード実行**：root 権限で動作するコードの埋め込み、SELinux ポリシーの無効化、
   `init_boot` / `boot` / `system` / `vendor` パーティションへのバックドア設置。
4. **利用者情報の窃取**：認証情報、通信内容、メッセージ、位置情報、決済アプリの取扱い情報等の窃取。
   改ざんした OS によるロック画面の偽装等も理論上可能。
5. **端末セキュリティ機構の無効化**：Verified Boot に依存する各種保護（改ざん検知、
   Key Attestation を利用したアプリ側の完全性検証等）の信頼性が損なわれる。
6. **サプライチェーン／中古端末流通経路での悪用（いわゆる evil maid 攻撃）**：
   端末を一時的に扱える立場の者（修理・中古買取・輸送・貸与端末の返却時等）が、
   検知困難な改ざんを施した端末を利用者に渡すことが可能。

**攻撃条件**：端末上で root 権限を取得できること（今回は既存のローカル権限昇格の脆弱性で達成）、
または端末への物理的アクセスによりパーティションへ書き込めること。
**ブートローダのアンロックは不要**であり、利用者による操作や承認も不要。

**CVSS v3.1（参考値・届出者評価）**
- 基本値：**8.2（High）**
- ベクタ：`CVSS:3.1/AV:L/AC:L/PR:H/UI:N/S:C/C:H/I:H/A:H`
- 選定理由：root 権限の取得を前提とする（PR:H）が、その一時的な侵害をブートローダのロックという
  端末の信頼境界を越えて恒久化させるため Scope は Changed（S:C）とした。
- 参考：物理アクセスによる書き込みを前提とする場合
  `CVSS:3.1/AV:P/AC:L/PR:N/UI:N/S:C/C:H/I:H/A:H`（基本値 7.6）

### 4-5. 回避策・対策

**利用者側の回避策**
- 有効な回避策はありません（署名鍵はファームウェアに固定されており、利用者設定では変更できません）。
  最新ファームウェアへのアップデートによっても解消されません（検証時点の最新版で確認）。
- 緩和策として、端末を第三者に物理的に預けない、信頼できない中古端末・貸与端末を業務利用しない、
  といった運用上の注意にとどまります。

**製品開発者側の推奨対策**
1. 出荷（user）ビルドの署名を、**製品開発者が秘匿管理する製品固有の AVB 鍵**に切り替える。
2. 併せて、ブートローダ／e-Fuse 側に焼き込まれた Root of Trust（AVB 公開鍵ハッシュ）を
   更新する必要があるため、出荷済み端末への配信可否・手順を検討する。
3. リリースビルドで `external/avb/test/data/` 配下の鍵が使用されないよう、
   ビルド設定（`BOARD_AVB_KEY_PATH` 等）を確認し、**テスト鍵が使われた場合にビルドを失敗させる
   チェックを CI／リリース工程に組み込む**（前掲の検査ツールはこの用途にも利用可能）。
4. 同一のビルド基盤を共用する他機種についても横展開して確認する。
5. AVB のロールバックインデックス運用（`rollback_index`）の適切な設定を併せて確認する。
6. 権限昇格の起点となったドライバ側の脆弱性（KGSL）についても、最新のセキュリティパッチ適用状況を確認する。
